# Friends Spring Boot Backend

Friends is a Spring Boot backend application that stores user data and allows users to create friendships. The primary data is stored in PostgreSQL. Changes are propagated asynchronously through Kafka to a read replica backed by MongoDB, which is used for efficient read operations. The system also includes an HTTPS API gateway.

Friend and friendship queries use token-based pagination designed to handle large datasets efficiently without loading all records into memory. The same pagination model is used when reading data from the primary service and from the MongoDB replica.

## Technology stack

- Java 21 and Spring Boot 4.1.0
- Spring Cloud Gateway Server WebFlux 2025.1.3
- Spring Web MVC for the application services
- PostgreSQL 16 with Spring Data JPA and Flyway migrations
- MongoDB 8 with a single-node replica set for the synchronized read model
- Redis 7 over TLS for application caching
- Apache Kafka 3.7 over TLS for asynchronous events
- Debezium 3.6 for PostgreSQL change-data capture
- Docker Compose for local orchestration
- OpenTelemetry and Grafana `otel-lgtm` for traces, metrics, and logs
- Springdoc OpenAPI / Swagger UI
- Gatling 3.15.1 with the Gatling Maven plugin for performance tests
- MapStruct, Lombok, Micrometer, Resilience4j, and Flamingock

## Database migrations

Database migrations are required when initializing the application:

- **Flyway** manages the PostgreSQL schema and runs as part of `user-service` startup.
- **Flamingock** manages MongoDB read-model migrations and runs as part of `user-service-sync` startup.

Both migration mechanisms must be enabled and allowed to complete before the services are considered ready. Docker Compose waits for the database health checks and initialization services before starting dependent application services.

## Services

| Service | Purpose | Local endpoint |
| --- | --- | --- |
| `gateway` | HTTPS entry point and routing | `https://localhost` |
| `user-service` | Users, friendships, PostgreSQL write model, Kafka producer | internal port `8080` |
| `user-service-sync` | Kafka consumer and MongoDB/Redis read model | internal port `8081` |
| `postgres-db` | Primary relational database | `localhost:5432` |
| `mongo-db` | MongoDB read model and replica set | `localhost:27017` |
| `redis` | TLS-enabled cache | `localhost:6379` |
| `kafka` | TLS-enabled event broker | `localhost:29092` |
| `debezium` | PostgreSQL CDC connector | `http://localhost:8083` |
| `lgtm-grafana` | Grafana, Loki, Tempo, and Prometheus-compatible telemetry | `http://localhost:3000` |

The gateway exposes the main service under `/main` and the read replica under `/replica`. The `user-service-sync` Compose service is scaled to two containers by default and both containers listen on internal port `8081`.

## Prerequisites

Install the following tools:

- Docker Engine or Docker Desktop with the Compose plugin
- JDK 21
- OpenSSL
- `keytool` from the JDK

The repository includes Maven Wrapper, so Maven does not need to be installed separately.

## Configuration

Non-secret configuration is stored in [`.env`](.env), including database usernames, database names, MongoDB replica-set name, and Kafka topic names.

Passwords are not stored in `.env` or passed as ordinary Docker Compose environment variables. They are mounted into containers as Docker secrets from the local `.secrets` directory:

- `POSTGRES_PASSWORD`
- `MONGO_DB_ROOT_PASSWORD`
- `KEY_PASSWORD`
- `KEYSTORE_PASSWORD`
- `kafka-credentials.properties`
- `debezium-credentials.properties`

The development values generated by the current script are:

- database passwords: `db_secure_password`
- key and keystore passwords: `secure_password`

Replace these values before using the project outside local development.

## Initialize secrets and TLS credentials

From the repository root, run:

```bash
./scripts/create_secrets.sh
./scripts/create_credentials.sh "$(<.secrets/KEYSTORE_PASSWORD)" "$(rg '^POSTGRES_USER=' .env | cut -d= -f2-)"
```

The second argument is the PostgreSQL username from `POSTGRES_USER` in `.env`. It is used when generating PostgreSQL's `pg_ident.conf`, so the certificate identity map matches the configured database user.

`create_secrets.sh` creates `.secrets` and writes the database and keystore passwords. `create_credentials.sh <keystore_password> <postgresql_user_name>` creates the development CA, service certificates, MongoDB replica-set keyfile, PKCS#12 keystores/truststores, PostgreSQL SSL configuration, and Kafka health-check client configuration under `.certs`.

The certificate script regenerates the contents of `.certs`. Do not run it if you need to preserve existing local certificates.

The generated directories are protected with mode `700`. The MongoDB entrypoint applies mode `600` to the replica-set keyfile and certificate files before startup. Do not commit `.secrets` or `.certs` security material.

## Start the complete stack

For a fresh checkout, the complete setup command creates secrets, generates certificates, builds all modules, and starts Docker Compose:

```bash
./scripts/package_and_deploy_all.sh SECRETS=true RENDER_KEYS=true
```

The script runs a Maven build, creates the secrets when `SECRETS=true`, creates TLS credentials when `RENDER_KEYS=true`, and starts the stack with the Compose project name `friends`.

After the initial setup, the generated files in `.secrets` and `.certs` are reused automatically. They do not need to be regenerated for every deployment.

Check the running containers with:

```bash
docker compose -p friends ps
docker compose -p friends logs -f gateway user-service user-service-sync
```

Useful URLs:

- Swagger UI: <https://localhost/swagger-ui/index.html>
- Gateway OpenAPI: <https://localhost/main/v3/api-docs>
- User Sync OpenAPI: <https://localhost/replica/v3/api-docs>
- Grafana/Tempo: <http://localhost:3000>

The gateway uses a development certificate, so clients may need to trust the generated CA or disable certificate verification for local-only testing.

## Start or rebuild one service

```bash
./scripts/package_and_deploy_service.sh gateway
./scripts/package_and_deploy_service.sh user-service
./scripts/package_and_deploy_service.sh user-service-sync
```

The service deployment script always uses the existing secrets and TLS credentials. It does not create or replace them. To replace credentials, run the credential-generation scripts explicitly, or use the complete-stack command described in [Start the complete stack](#start-the-complete-stack).

For a debug container with the remote debugger ports from `docker-compose.debug.yml`:

```bash
./scripts/package_and_deploy_service.sh DEBUG=true
```

Debug ports are `5004` for Gateway, `5005` for `user-service`, and `5006` for `user-service-sync`. Debug mode runs one `user-service-sync` instance.

## Run Gatling

Start the complete stack first. The Gatling simulation sends requests through the HTTPS gateway, creates users and friendships through `/main`, and then reads paginated data through both `/main` and `/replica`.

Run the simulation from the repository root:

```bash
./mvnw -pl user-service -am gatling:test \
  -Dgatling.simulationClass=com.example.demo.userServicePerformance.UserServiceSimulation  
```

The simulation currently:

1. Creates 8,000 users through the main route.
2. Creates friendships for one user.
3. Fetches paginated friends and friendships through the main route.
4. Fetches the same data through the replica route.

The read APIs use token-based pagination. This keeps response sizes bounded and allows the services to process large numbers of users and friendships incrementally.

Gatling HTML reports are generated below:

```text
user-service/target/gatling/
```

The test uses:

- Main protocol: `https://localhost/main`
- Replica protocol: `https://localhost/replica`
- User creation and friendship requests through Gateway
- Sequential pagination using the returned `nextPage.token`

If the Maven plugin asks for a simulation, select:

```text
com.example.demo.userServicePerformance.UserServiceSimulation
```

## Stop and clean up

Stop containers and remove Compose volumes with:

```bash
./scripts/cleanup.sh
```

This removes the Docker Compose volumes, including PostgreSQL, MongoDB, Kafka, and LGTM data. The local certificate and secret directories are not removed. To regenerate certificates after cleanup, run:

```bash
./scripts/create_credentials.sh "$(<.secrets/KEYSTORE_PASSWORD)" "$(rg '^POSTGRES_USER=' .env | cut -d= -f2-)"
```

## Observability

All Spring services export OpenTelemetry data to the LGTM container. Tracing is sampled at 100% in the current development configuration. The two `user-service-sync` instances use an instance attribute based on their container hostname, allowing them to be distinguished in Tempo.

Example TraceQL queries:

```text
{ resource.service.name = "gateway" }
{ resource.service.name = "user-service" }
{ resource.service.name = "user-service-sync" }
```

## Development notes

- The application services use TLS for PostgreSQL, MongoDB, Redis, Kafka, and HTTPS where configured.
- Java keystore passwords are supplied through Docker secrets and Spring Boot `configtree` import.
- Database usernames and topic names are intentionally kept in `.env`; passwords remain Docker secrets.
- `user-service` writes the primary model and publishes events. `user-service-sync` consumes Kafka events and maintains the MongoDB/Redis read model.
- Gateway routes are defined in `gateway/src/main/resources/users-gateway.properties` and `gateway/src/main/resources/users-sync-gateway.properties`.
